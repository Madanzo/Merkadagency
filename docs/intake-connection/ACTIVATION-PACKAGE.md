## Shared abuse control

Added an atomic server-only Firestore **global** budget before Siteverify/CRM. Each instance/region uses the same approved database and fixed `websiteIntakeAbuse/global-v1` document. A transaction admits at most the approved number per rolling-from-first-request60-second window; no IP, inquiry, key, token or CRM state is stored. The one fixed document holds only count/until and resets on the next admitted window; no TTL job, index, worker or new CRM store is needed. Missing/invalid configuration, corrupted state, database failure, transaction retries exhausted or a3-second deadline refuse forwarding. A late transaction may consume a slot, never admit late. Separate independent limiter objects are tested concurrently against the demo emulator. Emulator atomicity tests allow20 seconds, and the canonical fixture10 seconds, to isolate database contention from production deadline behavior; production remains3 seconds. Initial concurrent emulator requests exceeded the production deadline and correctly refused admission; this is an availability limitation, not a passed production load result. The bounded timeout/error tests verify fail-closed behavior separately. Real deployment latency/availability still requires acceptance.

This is a global cost/exposure ceiling, **not a per-person guarantee**. The process-local8/min socket bucket and8-active cap remain defense in depth.
